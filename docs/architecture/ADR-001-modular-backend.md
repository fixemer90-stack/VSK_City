# ADR-001: модульный backend и совместное размещение API/worker

Статус: Предложено. Решение описывает стартовую корпоративную архитектуру;
не отмечает её реализованной или утверждённой пользователем.

## Контекст

Нужна недорогая первая версия со стабильным миром, надёжным зачётом и отложенным сносом.
[CR-01–CR-05](CORPORATE-REQUIREMENTS.md) требуют отдельного Docker-образа backend,
конфигурации через env, stateless, PostgreSQL/Redis и условного S3/MinIO.
Они не требуют отдельного микросервиса на каждый логический модуль.
Формат внешнего источника пока неизвестен и отложен; это не блокирует проектирование
внутреннего расчёта и транзакционного хранения.

## Предлагаемое решение

- Единая backend-кодовая база ASP.NET Core/C# с логическими границами Adapter,
  Application, Engine, Layout, Persistence, Identity/Organization и Scene Queries.
- Начальная поставка — один Docker-образ/host для API и фоновой проверки сноса.
  Frontend Angular/PixiJS поставляется отдельно; PostgreSQL/Redis внешние.
- Все изменения мира проходят через общий прикладной путь и PostgreSQL-транзакцию.
  Worker не имеет отдельного неидемпотентного способа менять дома/опыт.
- Время, результаты, квитанции и сроки сохраняются вне процессов; sticky sessions не нужны.
- Интеграционный адаптер изолирован от ядра. Не создаются фиктивные Kafka/CSV/HTTP-контракты.
- Полный event sourcing, отдельный scheduler-сервис, брокер внутренних команд и
  отдельный сервис на каждую игровую операцию не входят в обязательную стартовую инфраструктуру.

Границы и потоки: [SYSTEM-ARCHITECTURE](SYSTEM-ARCHITECTURE.md).
Требования: [расчёт](../SRS/SRS-ENGINE.md) и [хранение](../SRS/SRS-STORAGE.md).

## Рассмотренные альтернативы

| Вариант | Почему не выбран базовым предложением |
| --- | --- |
| Микросервисы расчёта, геометрии, журнала и API с независимыми БД | Усложняют атомарный зачёт, поставку, наблюдаемость и восстановление без доказанной необходимости |
| Отдельный worker с первого дня | Допустим, но добавляет развёртываемую часть; пока нет измеренного основания выделять ресурсы/обновления отдельно |
| Память процесса/Redis как единственное состояние | Не соответствует корпоративным ограничениям и сохранению сроков/прогресса |
| Пересоздание мира из текущих итогов | Теряет историю распределения XP, исходные улицы и геометрию |

## Последствия и проверка

Преимущества: меньше развёртываемых компонентов, единая транзакционная граница,
независимое тестирование ядра, возможность заменить входной адаптер без переписывания расчёта.

Компромиссы: API и worker делят ресурсы и цикл обновления; нельзя безгранично выполнять
тяжёлые расчёты в HTTP-пути. Нужны ограниченные фоновые порции, диагностика и тесты конкуренции.
Точные бюджеты/интервалы определяются по нагрузкам, а не выдумываются сейчас.

Будущие проверки: работа двух backend-экземпляров без двойного зачёта/сноса;
restart между постановкой и deadline; потеря ответа после commit; потеря Redis;
отсутствие блокировки всего мира при независимых улицах в выбранной схеме.
Синтетический E01 не считается доказательством этих корпоративных проверок.

Пересмотреть решение, если измерения покажут взаимное влияние API и worker,
разные требования масштабирования/обновлений или обязательный стандарт корпоративной платформы.
При выделении worker сохраняются единое применение, семантическая идемпотентность
и PostgreSQL как источник истины; распределённая транзакция не появляется автоматически.
