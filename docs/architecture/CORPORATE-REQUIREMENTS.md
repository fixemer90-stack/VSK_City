# Корпоративные требования к сервису VSK City

Статус: обязательные ограничения подтверждены пользователем; реализация и runtime-проверки
не выполнены. Применяются при создании backend и инфраструктуры, не означают готовность
Docker-образа, миграций или развёртывания. Историческая концепция v0.3 не изменяется.

## CR-01. Отдельный Docker-образ

- Backend-сервис поставляется отдельным Docker-образом приложения.
- PostgreSQL, Redis и S3/MinIO — внешние зависимости, не процессы внутри образа backend.
- Один и тот же образ должен настраиваться для разных окружений без пересборки.
- Начальный backend может иметь единую кодовую базу с логическими модулями Ingestion,
  Engine, Map Generator и API. Требование отдельного образа само по себе не требует
  превращать каждый модуль в самостоятельный микросервис.
- Если позднее выделяется самостоятельный worker/микросервис, его упаковка и запуск
  описываются отдельно; преждевременное дробление не входит в текущую задачу.

## CR-02. Настройки через переменные окружения

- Адреса зависимостей, параметры подключений, учётные данные, настройки OIDC,
  интервалы импорта/опроса и параметры S3 передаются через переменные окружения.
- Не зашивать настройки корпоративного окружения и секреты в код, Dockerfile,
  образ или отслеживаемые конфигурационные файлы.
- Допустим безопасный .env.example с перечнем ключей без реальных секретов;
  реальные значения передаются средой развёртывания и не выводятся в логи.
- Обязательные настройки проверяются при старте; отсутствие обязательного значения
  не должно молча переключать сервис на другое окружение или локальную БД.
- Точные имена ключей и значения по умолчанию будут определены в исполняемом backend.
  Сейчас готового конфигурационного контракта нет.

## CR-03. Stateless-экземпляры приложения

- Между запросами и запусками экземпляр backend не хранит единственную копию
  бизнес-состояния в памяти процесса или на локальном диске контейнера.
- Улицы, геометрия, участки, опыт, парковки, зачёт договоров, обработанные изменения,
  версии и сроки сноса сохраняются во внешнем хранилище.
- Перезапуск или замена экземпляра не пересоздаёт мир и не меняет результаты продаж.
- Запросы не должны требовать привязки пользователя к определённой реплике.
- Таймер «Под снос» хранится в PostgreSQL. Повтор импорта и рестарт не запускают его заново;
  окончательное удаление и перераспределение опыта защищаются от повторного выполнения.
  Таймер в памяти процесса не может быть единственным механизмом выполнения сноса.
- Горизонтальное масштабирование требует транзакционной защиты от параллельного
  зачёта договора и двойного сноса. Конкретный механизм будет задан в техническом контракте.

Stateless относится к экземплярам приложения, а не к миру или самим PostgreSQL/Redis.
Сохранять состояние игры необходимо; восстанавливать его только из итоговых сумм нельзя.

## CR-04. PostgreSQL и Redis

- Корпоративные системы хранения — PostgreSQL и Redis; не вводить другую основную
  СУБД вместо PostgreSQL для рабочего сервиса.
- PostgreSQL — источник истины для игрового состояния, геометрии, связей,
  идемпотентности, версий и отложенных операций.
- Redis входит в целевой корпоративный стек как восстанавливаемый кеш/временное
  хранилище, не единственный носитель прогресса, журналов зачёта или сроков сноса.
- Потеря или очистка Redis не должна уничтожать продажи, менять геометрию или
  отменять/повторно выполнять снос; кеш восстанавливается из PostgreSQL.
- Наличие Redis в стеке не означает, что в него нужно переносить бизнес-состояние.
  Сценарии деградации доступности и точная область кеширования уточняются при реализации.

## CR-05. Файлы — S3 Object Storage / MinIO

- Если сервису потребуется постоянное хранение файлов — использовать S3-совместимое
  Object Storage, в корпоративном контуре MinIO.
- Загруженные файлы, сохраняемые выгрузки и экспорты не хранить постоянно на диске
  контейнера и не требовать общего локального каталога между репликами.
- В PostgreSQL хранить необходимые метаданные/ключи объектов, содержимое файлов — в S3.
- Endpoint, bucket, доступ и прочие параметры подключения передавать через env.
- Если сохраняемых файлов пока нет, не вводить обязательную файловую подсистему
  ради соответствия: требование условное, по факту появления такого сценария.
- Исходники, включённые при сборке статические ресурсы и локальные CSV тестового набора
  не являются механизмом постоянного файлового хранения рабочего сервиса.

## Будущая приёмка

Все проверки ниже ещё предстоит выполнить на реальном сервисе:

- [ ] Собрать и запустить отдельный образ backend с внешними PostgreSQL/Redis.
- [ ] Изменить окружение через env без пересборки образа; проверить отсутствие секретов в образе/логах.
- [ ] Перезапустить контейнер: улицы, геометрия, опыт и сохранённые сроки сноса не изменились.
- [ ] Проверить работу нескольких реплик без привязки сессий и без двойного зачёта/сноса.
- [ ] Очистить тестовый Redis: сохранённый прогресс остаётся в PostgreSQL, кеш восстанавливается.
- [ ] При наличии сохраняемых файлов проверить запись/чтение S3/MinIO после замены контейнера.

Контракты портов, registry, health/readiness, секретов платформы, миграций и точные версии
зависимостей определяются при реализации. Этот документ не заменяет их рабочие проверки.
